## Данные
```
1.  Shop API [INFO]
    1.1 Идентификатор заказчика
    1.2 Идентификатор заказа
    1.3 Статус заказа
    1.4 Временная метка
2. CRM API [INFO]
   1.1 Идентификатор менеджера
   1.2 Идентификатор заказа
   1.3 Статус заказа
   1.4 Временная метка
3. MES API [INFO]
   1.1 Идентификатор оператора
   1.2 Идентификатор заказа
   1.3 Статус заказа
   1.4 Временная метка

Shop API, CRM API, MES API [ERROR]
Ошибки при взаимодействии с другими сервисами
1. Статус код
2. Сервис
3. Текст ошибки
4. Временная метка

Shop API, CRM API, MES API [FATAL]
Ошибки при взаимодействии с объектами инфраструктуры
БД, брокер, с3
1. Объект инфраструктуры
2. Ошибка
3. Входные данные если были
```

## Мотивация.
При изучении инциндентов без наличия логов обычно не очень хорошо удается идентифицировать что произошло.
Внедрение логирования позволит видеть состояние заказа или системы в моменте времени и лучше справляться с поступающими проблемаи.

1. Повысить надёжность за счёт выявления и устранение дефектов
2. Повысить безопасность, к примеру, за счет отслеживания ддосных заказов
3. Отслеживать конверсию и анализировать на каком эатпе пользователи могут отменять заказы или получать ошибки.

## Предлагаемое решение.
1. Приложение будет логировать в поток вывода контейнера
2. Разворачиваем рядом с контейнером Fluentd
3. Fluentd забирает данные из вывода контейнера и
   отдаёт их в clickhouse
3. К логам будут иметь доступ разработчики по кредам.
   Также предлагаю закрыть доступн под корпоративный
   впн.
4. Логи будут писаться в таблицу и ротейтится раз в месяц. Храним последний месяц после чего данные удаляются. То есть в системе текущие логи + 1 месяц.
