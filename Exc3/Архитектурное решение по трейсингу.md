## Список данных для трейсинга.
1.  Сквозной идентификатор для построения трейса
2. Идентификатор заказа
3. Статус заказа
4. Временная метка попадания запроса в систему
5. Временная метка ответа системы
6. Статус код ответа системы
7. Название сервиса

## Мотивация.
Пользователи жалуются на просроченные заказы, команда разработки на текущий момент не имеет понятия почему это происходит. Мест где может "сломаться" или "зависнуть" заказ множество, чтобы понимать где произошел "затык" необходимо внедрить трейсинг.
Без внедрения трейсинга мы так и продолжим как слепые котята тыкаться и пытаться угадать в чём проблема, попутно теряя клиентов. Трейсинг просто необходим.
Внедрение трейсинга позволит понять где возникают деградации.
Для технической команды даст возможность отслеживать деградации сервисов и быстрее реагировать на инцинденты.

## Предлагаемое решение.
Нужно развернуть систему сбора трейсинга, которая
будет собирать данные и давать возможность их визуализировать. Внедрим open-source решение jaeger.
1. Развернуть jaeger collector
2. В сервисах подключить биоблиотеки opentelemetry
3. Рядом с сервисами развернуть jaeger agent, который
   будет посылать данные в коллектор
4. Развернуть хранилище, где будут храниться данные о
   трассировке, можно использовать prometheus(добавленный для мониторинга), который будет забирать данные из коллектора.
